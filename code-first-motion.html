从最小开始

为什么从一颗电机开始

你即将一次验证三件独立的事：(1) 代码能编译，(2) 部署到了 rio 上，(3) rio 能通过 CAN 跟电机控制器对话。如果一上来就写四个电机 + 摇杆的底盘代码，挂了你根本不知道是哪一环出问题。

一颗电机 + 一个按键 = 一条可追踪的信号链路。一旦出问题 —— 第一次部署通常都会出点问题 —— 你只有一条链可走，几分钟就能定位故障，而不是花上几个小时。

验证 1 代码能编译
验证 2 部署到了 rio
验证 3 rio 通过 CAN 对话
最终结果 一条可追踪链路

信号链路

从按下按键到电机转动

按下 A 键，信号要穿过八个框，电机才会转。这条链上每个框都可能挂掉。记住整条链路 = 知道该去哪儿查。 

   Driver presses A
   按下 A 键
        │
        ▼
   Driver Station laptop
   reads USB HID input
   笔记本读 USB HID 输入
        │
        ▼ (Wi-Fi / USB)
   roboRIO receives
   the joystick state
   roboRIO 收到摇杆状态
        │
        ▼  (your code, every 20 ms)
   Robot.teleopPeriodic():
     if (controller.getAButton())
        motor.set(0.5);
        │
        ▼  (Phoenix6 / REVLib library)
   CAN frame sent on the bus
   往 CAN 总线发一帧
        │
        ▼
   Motor controller (e.g. SparkMax id=5)
   receives "50% duty cycle"
   电机控制器收到 "50% 输出"
        │
        ▼  (3-phase output to the motor)
   Motor spins. 🎉
   电机转起来。🎉

最小代码

最小代码 — 暂用 TimedRobot，先不上 Command-Based

我们故意先不用 Command-Based。一颗电机用框架是过度设计，框架会把“实际发生的事”藏起来。先体会一遍裸循环，框架的价值后面才看得明白。 

// src/main/java/frc/robot/Robot.java
package frc.robot;

import com.revrobotics.spark.SparkMax;
import com.revrobotics.spark.SparkLowLevel.MotorType;
import edu.wpi.first.wpilibj.TimedRobot;
import edu.wpi.first.wpilibj.XboxController;

public class Robot extends TimedRobot {

    // boot-time: created once, lives forever.
    // 启动期：只创建一次，活到关机。
    private final SparkMax motor = new SparkMax(5, MotorType.kBrushless);
    private final XboxController driver = new XboxController(0);

    @Override
    public void teleopPeriodic() {
        // 20 ms tick: read input, write output, return.
        // 20ms 节拍：读输入、写输出、返回。
        if (driver.getAButton()) {
            motor.set(0.5);
        } else {
            motor.set(0.0);
        }
    }
}

注意这段代码里的三件事

  1. 01

    motor 是字段，不是局部变量

    它只创建一次，motor.set(...) 只是修改一个已经存在的对象的设定值。

  2. 02

    teleopPeriodic 几乎啥也没干

    读、写、返回。重活在 motor.set() 里（Phoenix6 / REVLib 负责构造 CAN 帧）。

  3. 03

    没有 while (true)

    WPILib 每 20 毫秒帮你跑一次这个方法。你自己写循环会把整个调度堵死，机器人直接挂。

生命周期细节

生命周期细节 — 从启动到节拍

现在是时候看清完整的“启动 + 节拍”流程了。这是 WPILib 官方 TimedRobot 模型：上电、创建字段、robotInit 跑一次，然后进入每 20 毫秒的分发循环。

每次排查“代码怎么不跑了”，第一句话永远是：我现在到底在哪个 periodic 里？这条搞对，80% 的 bug 都自己消失了。

  1. 01

    上电

    roboRIO 启动，WPILib 运行时开始工作。你的代码还没跑。

  2. 02

    new Robot() — 字段创建

    WPILib 构造你的 Robot 对象。每个字段 —— SparkMax、XboxController —— 都在启动时，恰好创建一次。

  3. 03

    robotInit() — 只跑一次（现在很少用）

    构造之后调用一次。现代代码大多把一次性初始化放在构造函数里，所以这个钩子常常留空。

  4. 04

    robotPeriodic() — 每 20 毫秒，无论什么模式都跑

    从此每个 20 毫秒节拍都从 robotPeriodic() 开始。disabled、autonomous、teleop、test 它都跑 —— 用来推 telemetry 和任何与模式无关的逻辑。

  5. 05

    模式分发 — 跑哪个 periodic？

    robotPeriodic() 之后，分发器检查 Driver Station 当前模式，只调用 disabledPeriodic()、autonomousPeriodic()、teleopPeriodic()、testPeriodic() 中的一个。然后下一个 20 毫秒节拍从第 04 步重复。

  6. 06

    模式切换 — *Init 跑一次

    在 Driver Station 从 disabled 切到 teleop 时，WPILib 先调用一次 teleopInit()，然后每 20 毫秒调用 teleopPeriodic()。再次 disable 则跑一次 disabledInit()。用 *Init 钩子在切换模式时调度 auto 命令、取消遗留任务。

TimedRobot 究竟是什么

TimedRobot 究竟是什么

你写下了 public class Robot extends TimedRobot。那个 extends 在背后干了一大堆活，值得专门讲清楚。

TimedRobot 是 WPILib 提供的 Java 基类，路径 edu.wpi.first.wpilibj.TimedRobot。它是当今几乎所有 FRC 机器人程序的基类。你写 extends TimedRobot 就是从它继承。在你一行代码都还没写之前，这个类已经替你准备好了什么？ 

   ┌──── what WPILib's TimedRobot already does for you ────────┐
   │                                                            │
   │  1. Boot:  Main.main() → RobotBase.startRobot(Robot::new)  │
   │     启动流程已经接好，你不用碰。                                │
   │                                                            │
   │  2. A 50 Hz hardware timer (20 ms ticks).                  │
   │     一个 50 赫兹的硬件定时器 (20 毫秒一拍)。                    │
   │                                                            │
   │  3. A mode dispatcher: every tick, checks the              │
   │     Driver Station's enabled/disabled state and current    │
   │     mode (disabled / autonomous / teleop / test) and       │
   │     calls the matching *Init (once on transition) and      │
   │     *Periodic (every tick).                                │
   │     一个模式分发器:每拍都查 Driver Station 当前模式,            │
   │     在模式切换时调一次 *Init, 每拍调一次 *Periodic.            │
   │                                                            │
   │  4. Empty default implementations of every hook:           │
   │     robotInit, robotPeriodic, disabledInit, disabledPeriodic, │
   │     autonomousInit, autonomousPeriodic,                    │
   │     teleopInit, teleopPeriodic,                            │
   │     testInit, testPeriodic,                                │
   │     simulationInit, simulationPeriodic                     │
   │     每个生命周期钩子的空实现都已经在那里。                       │
   └────────────────────────────────────────────────────────────┘

思维模型：钩子即插槽。每个 *Periodic 都是一个可选的插槽。无论你写没写，WPILib 每 20 毫秒都会调用它 —— 没重写就跑空实现，啥都不干。没有要求必须实现的抽象方法，也没有什么 start() 要你来调。框架在跑，你的重写插上去就行。 

// Roughly what TimedRobot looks like (real source is more elaborate):
// TimedRobot 大概长这样（真源码更复杂）:
public abstract class TimedRobot extends IterativeRobotBase {
    public TimedRobot() {
        // start a 20 ms hardware timer that calls loopFunc()
        // 启动一个 20 毫秒定时器，每次触发调用 loopFunc()
    }

    private void loopFunc() {
        robotPeriodic();              // always runs
        switch (driverStation.getMode()) {
            case DISABLED   -> disabledPeriodic();
            case AUTONOMOUS -> autonomousPeriodic();
            case TELEOP     -> teleopPeriodic();
            case TEST       -> testPeriodic();
        }
    }

    // Empty defaults — you override any subset.
    // 空的默认实现 —— 你重写其中任意几个即可。
    public void robotInit() {}
    public void robotPeriodic() {}
    public void teleopInit() {}
    public void teleopPeriodic() {}
    // ... and so on
}

基类的概念到此为止。里面没有藏着 scheduler，没有任何“框架魔法”。代码里凡是“自动发生”的事（“teleopPeriodic 怎么知道该跑了？”），答案永远是：TimedRobot 的硬件定时器 + 模式分发器。仅此而已。

为什么新手要懂这层

  • 它告诉你哪段代码该放哪里。只执行一次 → 构造函数 或 robotInit。每拍跑（不管什么模式）→ robotPeriodic。teleop 期间每拍跑 → teleopPeriodic。auto 期间每拍跑 → autonomousPeriodic。决策树就这么大。
  • 它告诉你为什么任何 *Periodic 里都不许写 while (true) —— 那等于偷走了定时器的控制权，后续节拍再也无法触发，机器人冻住。
  • 它告诉你 Command-Based 不是另一个基类。Command-Based 模板同样继承 TimedRobot，区别是往 periodic 里放什么 —— 这正是 Part 5 要讲的事。 （Part 5 →）

历史小注：WPILib 历年提供过几种机器人基类 —— SampleRobot（自己写循环，早已弃用）、IterativeRobot（更早的 periodic 风格，已替换）、TimedRobot（当前）。新项目只用 TimedRobot。Command-Based 模板就是继承它，再多加一个 RobotContainer 文件作伴。

常见的坑

常见的坑

第一次让电机动失败，几乎都是下面这几种。顺着信号链路从上往下逐一检查 —— 知道该看什么之后，断掉的那一环通常一眼就能看出来。

  1. 01

    在 *Periodic 里写 while (true)

    WPILib 已经每 20 毫秒调用一次这个方法。你自己写死循环会偷走定时器的控制权，后续节拍再也无法触发 —— 机器人冻住，Driver Station 掉线。读输入、写输出、返回就好。

  2. 02

    把电机当作 periodic 内的局部变量来创建

    电机必须是字段，启动时创建一次。如果在 teleopPeriodic 里写 new SparkMax(...)，你每秒会构造 50 个新对象 —— CAN 流量爆炸、设定值也不稳定。声明成 private final 字段。

  3. 03

    代码放错了 periodic

    如果按键判断写在 autonomousPeriodic 里，你却用 teleop enable，那就什么都不会发生。任何“按键没反应”的第一句话永远是：我现在到底在哪个 periodic 里？让你 enable 的模式和你写的 periodic 对上。

  4. 04

    CAN ID 写错，或用错厂商库

    new SparkMax(5, ...) 里的 ID 必须和控制器实际的 CAN ID 一致。代码里写 SparkMax 但总线上是 TalonFX，或者 ID 写错，CAN 帧就发到了空气里。先用 REV Hardware Client 或 Phoenix Tuner X 确认 ID 和电机类型。

  5. 05

    连上了但没 enable

    Driver Station 上 “Communications” 变绿只代表笔记本连上了 rio。还得点 Enable，电机才会动。连上 ≠ enable —— 怀疑代码之前先看 Enable 状态。
