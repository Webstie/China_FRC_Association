不用框架

不用框架硬塞一个 intake

假设你想在 A 键加个 intake —— 按住 A 吸入，松开停。最直觉的做法，就是在已有的底盘代码旁边，往 teleopPeriodic 里再塞两行。 

@Override
public void teleopPeriodic() {
    // drive / 底盘
    drive.arcadeDrive(-driver.getLeftY(), -driver.getRightX());

    // intake
    if (driver.getAButton()) intakeMotor.set(0.6);
    else                     intakeMotor.set(0.0);
}

这能用 —— 但只能撑住一个机构。接着再加一个需要预热 1 秒才能开火的 launcher、一个最后 30 秒才允许的 climber、一组检测到游戏件就变绿的 LED。teleopPeriodic 就变成一个挂满 timer 字段和 state flag 的巨型 if/else，全部塞在同一个文件里。

会坏掉的事

三件会坏掉的事

硬塞这种写法不会突然崩，而是慢慢腐烂。机构越堆越多，每一次都会冒出同样的三个结构性问题。这不是你写得差，而是“一个循环要干所有事”的必然结果。

手写并发 你成了 scheduler

预热计时、按键保持、LED 状态 —— 全靠你用 timer 字段和 boolean flag 手动追踪。你实际上在手动调度“谁什么时候跑”。又繁琐，又一不留神就错。

到处都是 timer + flag
硬件细节泄漏 motor.set() 散落各处

电机 ID 和 motor.set(...) 调用散落在整个文件里。改一个 CAN ID 就得全文搜索替换，而且没有任何一个地方“拥有”某个机构的硬件。

改 CAN ID 要全文搜索替换
没法组合 行为拼不到一起

“边开底盘边预热 launcher”不能写成 drive + launcher_spinup。你得把两段行为重新内联进来、手动合并各自的计时器 —— 每一种组合都是重写，而不是拼装。

每种组合都得重写

思维转变

思维转变 —— 一张愿望清单

先从 if/else 里抽身出来，问问自己到底想表达什么。不是“每 20 毫秒轮询这个按键、翻转那个 flag”，而是几句关于意图的大白话 —— 一张“机器人该怎么表现”的愿望清单。

把下面这几句读出来 —— 这就是那张愿望清单： 

"Hold A → run the intake."
"When match time is under 30 s → enable climb buttons."
"When auto starts → drive to the first scoring spot,
                    then shoot, then go pick up."

"按住 A → 跑 intake。"
"比赛剩下不到 30 秒 → 启用爬升按键。"
"Auto 一开始 → 开到第一个得分点 → 发射 → 回去捡。"

注意每一句的形状：一个 condition、一个 trigger、一个 action，以及涉及的 mechanism。没有一句提到轮询、计时器或 flag。你在描述“应该发生什么”，而不是事无巨细地管“每行代码什么时候跑”。你想写的这张愿望清单，和你被迫写出的 if/else，两者之间的落差 —— 正是这一页标题里那堵墙。

答案

这正是 Command-Based

再看一眼那张愿望清单。它讲的就是这样一种语言：在 condition 满足时被 trigger、使用特定 subsystem 的 Command。这套词汇不是你自己造的 —— WPILib 恰好直接提供了这套语言，它叫 Command-Based programming。

愿望清单里的每个词都对应框架里的一块：subsystem 持有硬件，command 描述动作，trigger 描述条件，再由一个 scheduler 在 50 赫兹下把它们连起来。下一页会把这四块讲透。

常见的坑

常见的坑

这里的坑不是语法错误，而是思维上的陷阱，会让新手在硬塞式写法早已不堪重负之后，还死守着它。早点识破它们，转向 Command-Based 就会变得理所当然，而不是吓人。

  1. 01

    以为 Command-Based 是 TimedRobot 的替代品

    它不是竞争关系。每个 Command-Based 项目的 Robot.java 仍然 extends TimedRobot —— 50 赫兹定时器和 *Periodic 钩子通通都在。Command-Based 是建立在 TimedRobot 之上的一种模式，不是把它换掉。

  2. 02

    非要等机器人“变大”才肯切换

    经验法则：一旦你有两个以上机构需要独立运行、又偶尔要协调，就已经超出 plain TimedRobot 的承载力了。每个赛季前两周就会到这一步 —— 那时就该切，别等 if/else 已经烂掉再说。

  3. 03

    想用手写实现组合

    “边开边预热”没法干净地手动合并 —— 最后你会把行为重新内联、把各自的计时器搅在一起。组合（sequence / parallel / race / deadline）正是框架白送给你的东西，别在一个循环里重新发明它。

  4. 04

    放任 motor.set() 在文件里蔓延

    一旦硬件访问漏进 teleopPeriodic，就没有任何一处“拥有”某个机构，改个 CAN ID 都得全文搜索替换。Subsystem 的全部意义，就是把 motor.set(...) 收在唯一一个地方。
