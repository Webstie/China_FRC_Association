每个机构都遵循的模式

每个机构都遵循同样的模式

intake 不过是一颗“你叫它转它就转”的电机。但把它接进机器人的方式，和你后面写 elevator、shooter、climber 的方式是完全相同的六步套路 —— 你以后写的每个 Subsystem 都一样。在这个最简单的机构上学一遍，剩下的都变成照抄改参。

按顺序走这六步。第 1–5 步都在 subsystems/ 下的一个文件里；第 6 步是 RobotContainer 里把按键连到命令的那一行。

第 1–5 步在这 subsystems/Intake.java
第 6 步在这 RobotContainer

六步走

六步，按顺序

就是这条流程。你做的每个机构都照它走，变的只有硬件和数字。

  1. 01

    新文件放 subsystems/

    每个机构一个文件。intake 有它自己的 Intake.java。

  2. 02

    extends SubsystemBase

    这个类继承 SubsystemBase。就这一行，你就拿到了 periodic()、Command factory method，以及自动的 requirement 追踪。

  3. 03

    硬件做 private 字段，构造函数里配置

    把电机控制器和传感器声明为 private final 字段。在构造函数里配置一次：current limit、idle mode、inversion。

  4. 04

    公开方法每个只做一件硬件动作

    每个 public 方法对硬件就是一个动作：run(speed)、stop()。代码库里别的地方都不直接碰电机。

  5. 05

    factory method 返回可调度的 Command

    像 intakeCommand() 这样的 factory method 返回一个能直接交给 binding 的 Command。因为是 subsystem 自己造的，这个 Command 会自动 require 本 subsystem。

  6. 06

    RobotContainer 里：创建 + 绑 Trigger

    在 RobotContainer 里创建这个 subsystem，再把某个按键的 Trigger 绑到它的命令上。一行：driver.a().whileTrue(intake.intakeCommand())。

Intake subsystem

写出 Intake subsystem

这就是整个 subsystem —— 第 1 到 5 步全在一个文件里。电机是 private 字段，构造函数里配一次。run() 和 stop() 各做一件硬件动作。intakeCommand() 是把现成 Command 交给 binding 的 factory method。 

// subsystems/Intake.java
public class Intake extends SubsystemBase {

    private final SparkMax motor = new SparkMax(
        Constants.IntakeConfig.INTAKE_MOTOR_ID,    // ← lives in Constants
        MotorType.kBrushless);

    public Intake() {
        // current limit, idle mode, inversion — set ONCE at boot.
        // 电流限制、idle 模式、反转 —— 启动时配一次。
    }

    @Override
    public void periodic() {
        // optional: push telemetry here. Runs every 20 ms automatically.
        // 可选：在这里推 telemetry。每 20ms 自动跑。
    }

    public void run(double speed) { motor.set(speed); }
    public void stop()            { motor.set(0); }

    // Command factory: "run while held."
    // factory method："按住就跑。"
    public Command intakeCommand() {
        return startEnd(
            () -> run(0.6),
            () -> stop()
        );
    }
}

三件值得注意的事 —— 你以后写的每个 subsystem 都会重复：

  1. 01

    CAN ID 来自 Constants，不内联

    电机的 CAN ID 从 Constants.IntakeConfig.INTAKE_MOTOR_ID 读取，而不是在这儿写个魔数。这是本队代码里就在执行的规矩 —— 每个 ID、gain、limit 都放 Constants，要改只有一个地方。

  2. 02

    periodic() 是常驻回调

    只要机器人开着就该 tick 的东西放进 periodic() —— 传感器读取、telemetry、简单状态机。Scheduler 每 20ms 自动调它，你永远不用自己调。

  3. 03

    startEnd 是 SubsystemBase 上的 factory method

    startEnd 是 SubsystemBase 提供的 Command factory：第一个 lambda 开始时跑一次，第二个 lambda 在命令结束或被中断时跑一次。因为是 subsystem 自己调的，返回的 Command 会自动 require 本 subsystem —— 不用自己写 addRequirements。

brushless 电机上有一项配置不要跳过：current limit。40 A 的 supply limit 是个不错的默认值 —— 它限制电机从电池抽多大的电流，这样卡死的 intake 不至于烧电机或跳 breaker。（stator current 和 supply current 是两套不同的限制；对第一个 intake 来说，supply limit 是保命的那个。）把它和 idle mode、inversion 一起写在构造函数里。

在 RobotContainer 里接线

在 RobotContainer 里接线

第 6 步。把这个 subsystem 创建为一个字段，再绑 A 键。上一页的 drive default command 原样留着 —— 你只是加上 intake。 

private final Intake intake = new Intake();

public RobotContainer() {
    // (drive default command code from Part 5 stays here)

    // Hold A → run intake. Release A → intake stops automatically
    // (because startEnd's second lambda fires when the command ends).
    // 按住 A → intake 跑。松开 A → intake 自动停
    // （因为命令结束时 startEnd 的第二个 lambda 会触发）。
    driver.a().whileTrue(intake.intakeCommand());
}

driver.a() 是一个 Trigger，.whileTrue(...) 的语义是“Trigger 为 true 时让 Command 一直被调度；一变 false 立即中断”。这一行就把 if-then 遥控写法里那一整个 if (driver.getAButton()) intake.run(0.6); else intake.stop(); 块替掉了。

把按键画成命令

把“按键 → 命令”画出来

一个 Trigger 是任意布尔信号源；binding method 把它连到一个 Command。下表对应本队 RobotContainer 给 driver / operator 的绑法 —— 你要绑的几乎所有东西都被这几个方法覆盖了。

触发源 绑定方法 行为
driver.a() .onTrue(cmd) 按下时触发一次。
driver.a() .whileTrue(cmd) 按住时跑，松开取消。
driver.a() .toggleOnTrue(cmd) 按一下开，再按一下关。
new Trigger(intake::hasGamepiece) .onTrue(cmd) 任何布尔值都能当 Trigger。
driver.a().and(driver.b())
driver.a().or(driver.x())		 .negate() 组合触发源 —— and / or / negate 在绑定前把布尔信号拼起来。

挑对方法 = 设计。本队代码里 onTrue 用于状态切换，whileTrue 用于按住执行。自己绑完一个 intake 后再去看他们的 configureBindings()，每个选择都会一目了然。

常见的坑

常见的坑

intake 很简单，但接第一个机构时几乎所有人都会撞上同样的几个坑。每一个，踩过一次以后就再也不会上当。

  1. 01

    想要 whileTrue 却用了 onTrue

    onTrue 在按下时调度一次就不管了。配上 intakeCommand() 这种自己不会结束的命令，松开按键后 intake 还在转。要“按住才跑”就用 whileTrue，松开 A 时命令被中断、stop() 触发。

  2. 02

    把 CAN ID 写死在内联里

    new SparkMax(5, ...) 能跑，直到接线一改，你就得在各个 subsystem 里翻那个数字。改成从 Constants 读，跟本队代码一样 —— 一处可改，不会有惊喜。

  3. 03

    brushless 电机没设 current limit

    不设 current limit，卡死的 intake（卡了游戏件、滚轮咬死）会把电池能给的电流全抽走，烧电机或跳 breaker。在构造函数里设个 supply current limit —— 40 A 是个合理的默认值。

  4. 04

    在 RobotContainer 里直接调 motor.set()

    subsystem 的全部意义就是让硬件只在一个地方出现。motor.set() 一旦漏进接线文件，Scheduler 就追踪不到 requirement，冲突检测失效。把硬件访问留在 Intake 里，让 binding 去调它的方法。

  5. 05

    把同一个 Command 实例绑到两个地方

    同一个 Command 同一时刻只能被调度一次。永远通过 factory method 构造 —— intake.intakeCommand() —— 让每个 binding 拿到一个新实例，而不是把一个 Command 存进字段再绑两次。

去哪读更多

去哪读更多

intake 是一个能扩展到机器人上每个机构的模式的最小版本。想要完整参考时，下面这些官方文档讲得更深。

  • WPILib — Subsystems — SubsystemBase 的约定、periodic()，以及 Command factory method（run、startEnd、runEnd）。
  • WPILib — Binding Commands to Triggers — 完整的 binding method 列表（onTrue、whileTrue、toggleOnTrue、onFalse）以及怎么组合 Trigger。
  • WPILib — CommandXboxController — 每个按键和模拟输入都是一个现成的 Trigger。
  • REVLib docs — SparkMax / SparkFlex 配置：smart current limit、idle mode、inversion、soft limit。
  • Phoenix 6 docs — 如果你的 intake 用 TalonFX：stator 与 supply current limit、neutral mode、follower mode。

最值得做的：去 Open Alliance 上读一支顶级队伍的 RobotContainer。他们的 configureBindings() 就是你刚写的那套 Trigger 到 Command 的接线，只是机构更多。 

// The shape never changes — just more lines of the same thing:
driver.a().whileTrue(intake.intakeCommand());
driver.b().whileTrue(shooter.spinUpCommand());
driver.x().toggleOnTrue(climber.climbCommand());
operator.povUp().onTrue(elevator.raiseCommand());
