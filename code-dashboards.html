是什么 & 为什么

Dashboard 是什么

Dashboard 是笔记本上的一个窗口，显示机器人代码发布出来的内容。所有 dashboard 都共享同一个底层传输：NetworkTables 4 (NT4)。代码发布 → 任何订阅的 dashboard 都能显示。

右边这张图就是全部的心智模型：机器人代码发布到 rio 上运行的 NT4 服务器，SmartDashboard、Shuffleboard、Elastic 和 AdvantageScope 都订阅同一个服务器。它们是同一份数据的不同窗口，不是不同的发布机制。

底层传输 NetworkTables 4
服务器在 rio 上
代码负责 发布 publish
Dashboard 负责 订阅 subscribe

NT4 生态

一个数据源，许多窗口

rio 上的机器人代码只发布一次。NT4 服务器把数据分发给每一个订阅的 dashboard。SmartDashboard、Shuffleboard、Elastic 是面向驾驶员的 dashboard；AdvantageScope 是程序员的窗口，可以同时订阅同一份实时数据。

比赛日

比赛日选哪个

常用的 dashboard 有四个，它们不能互相替代。三个面向驾驶员，一个（AdvantageScope）是程序员的工具。用下面这张表挑对场合 — 记住同一份发布出来的值会同时出现在它们里面。

Dashboard 什么时候选
SmartDashboard 临时 debug 写写就行，别用它做正式比赛 UI。
Shuffleboard 成熟、分页、官方。比赛 UI 第一选择。
Elastic 平板/手机友好，JSON 配置布局，2024+ 越来越多队伍换它。新队伍推荐。
AdvantageScope 不是给驾驶员看的，是程序员的窗口。实时 + 日志回放 + 3D 场地 + 曲线 + 手柄状态。调参和赛后分析必备。

最省事的搭配

新手最省事的搭配

其实不用二选一 — 关键是谁看哪个窗口。驾驶手和操作手看一个面向驾驶员的 dashboard；程序员看 AdvantageScope。同样发布出来的数据，两种完全不同的视角。

驾驶 / 操作手视角 Elastic

驾驶 / 操作手看 Elastic（或 Shuffleboard）：电压、比赛时间、选中的 auto、视觉状态、"有球"指示灯、2D 场地。

或 Shuffleboard
程序员视角 AdvantageScope

程序员调参时用 AdvantageScope。同样的数据，更强的可视化：3D 场地、曲线图、mechanism2d、手柄状态，赛后还能回放日志。

实时 + 日志回放

发布数值

让一个值上 dashboard

让一个值出现在任意 dashboard 上就这么一行。SmartDashboard.putNumber / putBoolean / putString 用一个字符串 key 发布单个值。用 "Drive/leftMeters" 这样的路径式 key，可以把相关的值归到一个文件夹里。

做 auto 选择器时，用 putData 发布一个 SendableChooser。chooser 会在 dashboard 上显示成一个下拉框，驾驶员选中的内容在代码里用 chooser.getSelected() 读回来。

就这些。同一行代码同时点亮 SmartDashboard、Shuffleboard、Elastic 和 AdvantageScope。它们是同一份数据的不同窗口，不是不同的发布机制。 

// All it takes to make a value appear on any dashboard:
// 让一个值出现在任意 dashboard 上就这么一行：
SmartDashboard.putNumber("Drive/leftMeters", drive.getLeftDistanceMeters());
SmartDashboard.putBoolean("Intake/hasPiece", intake.hasPiece());

// Or as a Sendable Chooser (auto picker):
// 或者一个可发送的选择器（auto 选择）：
SmartDashboard.putData("Auto Chooser", autoChooser);

NetworkTables 4

NetworkTables 基础

每个 dashboard 底下都是 NT4 —— 在机器人和你的笔记本之间搬运数据的协议。你很少直接碰它，但理解关于它的三件事，就能解释 dashboard 上几乎所有的怪现象。

  1. 01

    NT4 协议

    NT4 是所有 dashboard 共享的底层传输。代码把值发布到命名的表里，任何订阅了这些表的已连接 dashboard 都会通过网络收到更新。同一个协议，多个客户端。

  2. 02

    Topic、publisher、subscriber

    每个值挂在一个 topic 下（就是那个字符串 key，比如 "Drive/leftMeters"）。机器人代码是写入这个 topic 的 publisher；每个 dashboard 是从中读取的 subscriber。带斜杠的路径式 key 会把 topic 嵌套成文件夹，便于整理。

  3. 03

    服务器在 rio 上

    NT4 服务器跑在 roboRIO 上。你笔记本上的 dashboard 作为客户端连上去。这就是为什么机器人代码没部署运行时 dashboard 一片空白，也是为什么 rio 一回来一切就自动重连。

常见的坑

常见的坑

telemetry 看起来不花钱，直到它开始花钱。下面三个反复出现的坑制造了 dashboard 相关的大部分困惑 —— 空白控件、卡顿的循环、莫名其妙跳变的值。

  1. 01

    把 telemetry 塞进一个紧凑的内层循环

    每个 tick 里调几百次 SmartDashboard.put...，或者把它放进逐采样的循环，会拖慢一切。每个 periodic() 以 50 赫兹发布一次就够了，对 dashboard 来说绰绰有余。

  2. 02

    同一个 key 从多个地方写

    如果代码里两处都往同一个 topic 名发布，它们会互相打架，显示出来的值在两者之间闪烁。每个值给一个所有者、一个唯一的 key —— 用路径式 key 把它们区分开。

  3. 03

    读一个 topic 之前忘了先发布它

    绑定到从未发布过的 topic 的 dashboard 控件什么都不显示，或显示一个过期的默认值。如果某个值在 dashboard 上缺失，先确认那行发布代码真的跑到了（如果它在一个从不执行的分支里就不会跑）。
