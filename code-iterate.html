部署迭代循环

这赛季你要跑一百次的循环

在机器人上的几乎所有时间，你都耗在同一个小循环里：改代码、编译、上传到 roboRIO、在 Driver Station 里 enable、看它怎么动。能跑就 commit 然后下一个；不能跑，答案几乎总在 DS 控制台或 riolog 里 —— 所以先看再改。

  1. 01

    Edit — 改代码

    在 VS Code 里做一处小的、可验证的改动。改得越小越好调试：出问题时你清楚知道改了什么。

  2. 02

    Build (Ctrl+Shift+P → Build)

    编译项目。编译错误在你笔记本上就被抓住，根本不会传到机器人。先把红色波浪线修掉 —— 编不过的代码不要部署。

  3. 03

    Deploy (Ctrl+Shift+P → Deploy)

    把编译好的代码通过电台（或 USB）上传到 roboRIO。完成后，rio 会用新代码重启你的机器人程序。

  4. 04

    在 Driver Station 启用

    选一个模式（Teleop / Auto / Test）再按 Enable。机器人没 enable 之前，你代码对电机做的任何事都不会发生 —— disabled 意味着硬件被锁在安全状态。

  5. 05

    验证行为

    看真实机器人（或 sim）。按键有没有做你预期的事？机构方向、速度对不对？拿你想要的结果去比，而不是拿“它动了”去比。

  6. 06

    能跑吗？能 → commit、push、下一个

    行为对了，就 commit 这次改动并 push，让它有备份、队友也能拿到。然后开始下一个小改动。

  7. 07

    不能跑？→ 看 DS 控制台或 riolog，再回到 Edit

    不对，就看 Driver Station 控制台或 riolog。stack trace 或你的 println 输出会告诉你发生了什么。先读，再回到第 1 步改代码。别盲目猜测后反复重传。

看 Driver Station

看 Driver Station

Driver Station 顶部的三盏灯，几乎说明了机器人的全部状态。在动别的之前先学会读它们 —— 它们一眼就能回答“机器人准备好了吗”和“哪里坏了”。 

   Communications  │  Robot Code  │  Joysticks
   通信             │  代码         │  摇杆
   ──────────────────────────────────────────────
   green           │  green       │  green        → ready to drive / 可以驾驶
   green           │  RED         │  any          → code crashed; read console
                                                     代码挂了，看控制台
   RED             │  any         │  any          → rio not reachable;
                                                     check radio / cables / IP
                                                     连不上 rio，查电台 / 线 / IP
灯 / 状态 含义 怎么办
通信绿 · 代码绿 · 摇杆绿 能连上 rio，你的代码在跑，至少绑了一个手柄。 可以驾驶。选模式、Enable。
通信绿 · 代码红 能连上 rio，但你的机器人程序崩了或起不来。 看灯下面的 Driver Station 控制台 —— 有一条 stack trace，99% 是 NullPointerException。
通信红 笔记本根本连不上 rio，此时代码和摇杆灯都无所谓。 查电台、网线，以及队号 IP / wpilib_preferences。

Robot Code 红了，答案永远在那三盏灯下面的控制台里。先看再 Google。

症状速查

新手常见症状速查

新手大部分问题都能归到几个症状，每个症状都有一个“先看哪里”。在左列里找到你的症状，先去右列那个地方查，再做其他动作。

症状 先看哪里
部署报 “no route to host” 队号写错了 —— 看 .wpilib/wpilib_preferences.json。
部署后 Robot Code 一直红 DS 控制台里有 stack trace，99% 是 NullPointerException。
按键没反应 (1) robotPeriodic 里漏写 CommandScheduler.getInstance().run();。(2) 绑定方法选错了（onTrue vs whileTrue）。
走反方向 电机或摇杆方向反了。永远在代码里反，别动线。
一颗电机不转 (1) CAN ID 冲突。(2) 用错了厂家库。去 Phoenix Tuner X / REV Hardware Client 看设备列表。
loop overrun 警告 periodic() / execute() 里干了重活。挪出去，或降频运行。

调试在哪看

调试在哪看

行为不对的时候，别猜，去读。两个窗口让你看到机器人到底在说什么；三类反复出现的信息（stack trace、loop overrun、brownout）涵盖了你新手赛季会碰到的绝大多数情况。下面是它们各自在哪、怎么读。

在 Driver Station 里 DS 控制台

三盏灯下面的消息窗口。代码打到 stdout / stderr 的所有内容都在这里，机器人程序崩溃时的 stack trace 也在这里。比起到处撒 System.out.println，更建议用正经的 logging —— 但起步阶段 println 也够用。

stdout / stderr + 崩溃栈
在 VS Code 里 riolog

VS Code 里的机器人输出实时流，内容和 DS 控制台一样。它会在你的队号网络上自动发现 rio，让你不用切到 Driver Station 就能看日志。在笔记本前连续迭代时特别顺手。

实时流 · 自动发现
读栈 Stack traces

NullPointerException 最常见 —— 通常是某个字段没赋值（电机在错的地方创建、subsystem 是 null）。NoClassDefFoundError 表示某个 vendor dependency 版本对不上。“CAN id X not responding” 这类信息表示设备不在总线上或 ID 写错了。

NPE · NoClassDefFoundError · CAN ID 错
一类反复出现的警告 Loop overruns

机器人循环每 20 毫秒（50 赫兹）跑一次。如果你的 periodic() 或 execute() 跑得比这还久，DS 会打 loop overrun 警告，动作变卡。修法是把重活挪出去、用计数器降频运行，或在节拍之间缓存结果。

20 毫秒节拍 · 50 赫兹
一类电源警告 Brownouts

电池在负载下电压掉到约 6.8 V 时，rio 会 brownout 并切电自保 —— 机器人会抽动或动作中途趴窝。常见原因是电池没电，或太多电机同时拉电流。软件上的修法是加 current limit；硬件上的修法是换一块刚充满的电池。

~6.8 V · current limit

还有一个省下大量困惑的小检查：确认部署真的生效了。部署后看控制台里的 boot log 时间戳和 Robot Code 的 “running” 指示灯 —— 如果时间戳没变，你测的是旧代码。

第一天就用 Git

第一天就用 Git

在一支真正运转的队伍里，Git 不是可选项。多个程序员改同一个项目、部署可能覆盖掉能跑的代码、比赛时你得在几秒内回滚到一个已知能跑的版本。第一天就开始用 —— 下面三条规则能防住 90% 的赛季事故。

  1. 01

    比赛前每一个能跑的版本都打 tag

    比赛前，每一个已知能跑的版本都 git tag chs-week1-final。tag 是给某个 commit 打的永久标签，让你永远能回滚到一个确定能跑的版本 —— 哪怕赛场边改了一整天乱七八糟的东西。

  2. 02

    赛场上别动 main

    比赛时，main 始终保持“可比赛部署”状态。开一个分支（fix/intake-jitter）、测、再合。直接改 main 意味着一处坏改动就能毁掉你下一场要用的版本。

  3. 03

    vendordeps/ 和 pathplanner/ 必须提交；build/、.gradle/、.idea/ 绝对不提交

    vendordeps/（vendor 库描述文件）和 pathplanner/（你的 path 和 auto）是项目的一部分 —— 必须提交。build/、.gradle/、.idea/ 是生成出来的垃圾，会把仓库撑爆 —— 用标准的 FRC .gitignore，让它们被自动排除。

必会的几条命令

一整个赛季其实就靠这几条。clone 一次，然后 status / pull / add / commit / push 是每天的循环，checkout -b 用来开新的 feature 分支。 

# Get the team repo onto your laptop (once)
# 把队伍仓库拉到你的笔记本（只做一次）
git clone https://github.com/your-team/robot-2026.git

# What changed? Run this constantly.
# 改了什么？随时跑这条。
git status

# Get teammates' latest work before you start
# 开工前先拉队友的最新进度
git pull

# Stage and record a change
# 暂存并记录一次改动
git add .
git commit -m "Tune intake current limit to 40A"

# Send your commits to GitHub so others have them
# 把你的 commit 推到 GitHub，让别人也能拿到
git push

# Start a feature branch (don't work on main)
# 开一个 feature 分支（别在 main 上干活）
git checkout -b feature/auto-aim

# Bring a finished branch's work back into your branch
# 把一个已完成分支的成果合回当前分支
git merge feature/auto-aim

一套够用的分支模型

小队伍不需要花哨的东西。让 main 永远可部署，用一个 dev 分支整合进行中的工作，每件事开一个短命的 feature/* 分支。比赛版本用 comp-week-N 这样的 tag（或分支）标记，方便日后找回。 

main          ── competition-deployable, always works
              ── 可比赛部署，永远能跑
dev           ── integration of finished features
              ── 已完成 feature 的整合分支
feature/*     ── one branch per piece of WIP
              ── 每件进行中的工作一个分支
comp-week-N   ── tag (or branch) marking a competition build
              ── 标记某次比赛版本的 tag 或分支

标准的 FRC .gitignore

WPILib 项目自带一份 .gitignore。原则是：生成的东西全忽略，你写的或你依赖的东西全提交。新手最容易弄错的两点，就是把 vendordeps/ 和 pathplanner/ 留下，把 build/ 排除掉。 

# Generated — DO NOT commit / 生成物 —— 不要提交
build/
.gradle/
.idea/

# Keep these — they ARE the project / 保留 —— 它们就是项目本身
# vendordeps/   vendor library descriptors / vendor 库描述
# pathplanner/  your paths and autos / 你的 path 和 auto
# deploy/       files deployed to the rio / 部署到 rio 的文件

给比赛版本打 tag

带注释的 tag（-a）会记录是谁、在什么时候打的。tag 默认不会被 push —— 你得显式地 push 它们。养成这个习惯，决定了你是“10 秒就能回滚”，还是“能跑的代码丢了”。 

# Tag the current known-good build
# 给当前已知能跑的版本打 tag
git tag -a chs-week1-final -m "CHS Week 1, last known good"

# Tags aren't pushed automatically — push it
# tag 不会自动推送 —— 手动推
git push origin chs-week1-final

# Later, roll back to that exact build
# 之后，回滚到那个确切的版本
git checkout chs-week1-final

常见的坑

常见的坑

迭代循环和 Git 各自都有几个反复出现的坑。踩过一次就再也不难辨认 —— 但每一个第一次踩到时都会耗掉真实的赛场时间。

  1. 01

    改了代码但忘了部署

    你改了、编了、测了 —— 但跳过了 Deploy，rio 上跑的还是旧代码。不管你怎么调，行为都不变。永远用 boot log 时间戳确认部署生效了。

  2. 02

    sim 和比赛共用一份 Constants，单位却不一致

    用同一份 Constants 跑 sim 和真机，但单位不统一（米 vs 英寸、弧度 vs 角度），就会出现“sim 里没事、上场就崩”的数字。定一套单位约定并坚持。

  3. 03

    比赛中 disabled 时重启机器人代码

    别因为当前是 disabled 就在比赛中途重启机器人代码。重启要时间，如果在 rio 恢复前比赛 enable 了，你就死在场上。等到这场比赛结束再说。

  4. 04

    提交了 build/ 把仓库撑爆

    提交生成出来的 build/ 目录会用每次编译都变的文件把仓库撑爆。用标准 FRC .gitignore，让生成物永远不被追踪。

  5. 05

    比赛时直接改 main

    在 main 上一处坏的赛场改动，就毁掉你下一场要用的版本，且没有干净版本可退。开分支、测、合 —— 并保留一个打了 tag 的已知能跑版本可回滚。

  6. 06

    force-push 覆盖掉队友的工作

    一次 git push --force 能抹掉队友已经推上去的 commit。先 pull、解掉冲突，别对共享分支 force-push。在没备份的情况下往已有项目上 clone，也会以同样的方式丢掉未提交的工作。
