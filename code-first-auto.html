在生命周期里的位置

Auto 只是一条定时跑的 Command

Auto 只是“一条在自动赛阶段那 15 秒里跑的 Command”。同样的 Command 类、同样的 scheduler。新增的只有一件事：调度时机。

下面这条时序就是全部。Driver Station enable 到 auto，Robot.java 向 RobotContainer 要那条 auto Command 并 schedule 它，scheduler 每 20 毫秒推一拍；teleop 一开始，auto 被取消，控制权交回驾驶员。

autonomousInit() 做的事 只 schedule 一次
循环由谁推动 CommandScheduler
teleopInit() 必须 取消 auto 命令
窗口长度 15 秒

schedule → tick → cancelAll

调度 → 滴答 → 取消 这条流程

两条事实解释了 auto 的其余一切。其一，autonomousInit() 只 schedule 一次命令，后面 scheduler 一拍一拍推动它，你不用写循环。其二，teleopInit() 必须取消 auto 命令，否则它会一直跑进 teleop，跟驾驶员抢底盘。

  1. 01

    Driver Station：Enable + Autonomous

    比赛开始。Driver Station 把机器人切到 Autonomous 模式并 enable。WPILib 调用一次 Robot.autonomousInit()。

  2. 02

    Robot.java → RobotContainer.getAutonomousCommand()

    Robot.java 通过 getAutonomousCommand() 向 RobotContainer 要那条 auto Command。RobotContainer 返回一条可直接调度的 Command。

  3. 03

    CommandScheduler.schedule(auto)

    Robot.java 把这条 Command 交给 scheduler，仅此一次。这一行 schedule() 就是 autonomousInit() 的全部 —— 没有循环，没有状态机。

  4. 04

    每 20 毫秒 —— scheduler 推动 auto Command

    接下来 scheduler 在正常的 20 毫秒 / 50 赫兹循环上推进 auto Command：execute()、isFinished() 等等。这跟机器人上其他一切用的是同一拍。

  5. 05

    Driver Station：Enable + Teleop → cancelAll()

    teleop 开始时，teleopInit() 取消 auto 命令（cancelAll，或取消那条具体命令）。auto 停下，每个 subsystem 的 default command 恢复 —— 驾驶员重新拿回机器人。

拿 mobility 分

能拿 mobility 分的最简 auto

一条“前进两秒”的定时命令。该有的零件都齐了。这个 factory method 写在 Drive subsystem 上、返回一个 Command：run(...) 在命令存活期间每 20 毫秒驱动一次，.withTimeout(seconds) 让它结束，.finallyDo(...) 在末尾把机器人安全停住。 

// In Drive subsystem — a factory that returns a Command:
public Command driveForwardTime(double seconds, double speed) {
    return run(() -> arcade(speed, 0))   // every 20 ms while alive
        .withTimeout(seconds)             // ends after `seconds`
        .finallyDo(() -> arcade(0, 0));   // safe stop at end
}
// In RobotContainer — pick the auto:
public Command getAutonomousCommand() {
    return drive.driveForwardTime(2.0, 0.4);
}

走一遍流程

  1. 01

    Driver Station enable，设到 auto 模式

    比赛在自动赛阶段开局。

  2. 02

    Robot.autonomousInit() → container.getAutonomousCommand()

    Robot.autonomousInit() 调用 container.getAutonomousCommand()，拿到我们的命令。

  3. 03

    Scheduler 开始滴答 —— 每 20 毫秒一次 execute()

    每 20 毫秒 scheduler 调一次命令的 execute()（跑 run 里的 lambda → arcade(0.4, 0)）。

  4. 04

    2 秒后，withTimeout 把命令标记为结束

    2 秒后 .withTimeout(2.0) 把命令标记为结束。

  5. 05

    finallyDo 触发一次 → arcade(0, 0) → 安全停下

    finallyDo 触发一次 → arcade(0, 0) → 机器人安全停下。

这就是组合。run(...) + .withTimeout(2.0) + .finallyDo(...) 三块拼到一起。你没写状态机 —— scheduler 就是状态机。

auto 选择器

加一个 auto chooser

比赛策略上不止一个 auto。WPILib 的 SendableChooser<Command> 会在 Driver Station / dashboard 上显示成一个下拉框。你在 RobotContainer 构造函数里搭好它，每条 Command 注册成一个选项，用 SmartDashboard.putData 发布，getAutonomousCommand() 只要返回下拉框当前选中的那条就行。

  • setDefaultOption(...) — 在没人动下拉框前就预选中的那个选项。要选个安全的。
  • addOption(...) — 其余每个选项，包括一个 Commands.none() 的“什么都不做”。
  • getSelected() — 返回驾驶员选中的 Command；在 getAutonomousCommand() 里调用。
private final SendableChooser<Command> autoChooser = new SendableChooser<>();

public RobotContainer() {
    // ... drive default command, button bindings ...

    autoChooser.setDefaultOption("Drive forward 2s",
        drive.driveForwardTime(2.0, 0.4));
    autoChooser.addOption("Do nothing",
        Commands.none());

    SmartDashboard.putData("Auto Chooser", autoChooser);
}

public Command getAutonomousCommand() {
    return autoChooser.getSelected();
}

成熟队伍用的是 PathPlanner 的 AutoBuilder.buildAutoChooser()，逻辑完全相同，只是选项从 .auto 文件加载而不是内联。骨架一模一样。

进化路径

Auto 的进化路径

每一步只多一个新概念：编码器 → PID → 运动学 → 样条 → 协同。好消息是：FRC 里所有 auto，哪怕顶级队那种“快速定点自动得分”的庞然大物，骨架依然是本页开头那一个 getAutonomousCommand() 模式，只是积木更大块。

  1. 01

    定时前进

    run(...) + .withTimeout(...)。完全不读传感器 —— 就是“前进 N 秒”。够拿 mobility 分。

  2. 02

    闭环到位

    加上编码器。用 closed-loop / PID controller 代替秒表，开到精确的距离再停在目标上。

  3. 03

    多步顺序

    把小命令拼成 sequence：开过去、得分、再开。还是没有新框架 —— 就是组合。

  4. 04

    路径跟随（PathPlanner / Choreo）

    加上运动学和样条。沿着场上真实的轨迹开，而不是直线段。GUI 工具就是在这一步登场。

  5. 05

    多机构得分流程

    用事件标记把底盘、intake、shooter 协同起来 —— 一套完整得分流程。同一个模式，最大块的积木。

从“定时前进”到“沿着场上画好的路线开”，中间需要一条轨迹 —— 一个从时间到 (位姿, 速度) 的函数。理论上你能手算，实际上没人手算。FRC 里有两款 GUI 应用占据了这块：PathPlanner 和 Choreo。

用 GUI 画轨迹

用 GUI 画轨迹

你几乎从不手写轨迹。下面两款工具都是独立的桌面应用，跟 VS Code 并排开着用。你在当年场地图上拖航点，工具把 path / trajectory 文件存进你的项目，代码再把它当成一个 Command 加载。接入模式 —— 启动期配置一次、注册命名命令、构造 auto chooser —— 跟你上面已经见过的 SendableChooser 骨架一模一样。

两者“画好再加载”的流程相同，但选轨迹的方式不同：PathPlanner 手画顺滑的样条，Choreo 在物理模型上跑数值优化器、算出时间最优的那条。每个工具各有一页 —— 先从 PathPlanner 入门。

手画样条 PathPlanner

拖航点，它在航点之间画顺滑样条并算出轨迹，把 .path / .auto 文件存到 deploy/pathplanner/ 下。上手快（点 → 拖 → 完事），事件标记能把路径直接变成完整得分流程、代码不用改。样条顺滑但不时间最优。新手默认就用它 —— 多数队伍的 Week 1 auto 都是在这画的。

PathPlannerLib · AutoBuilder.configure(...)

打开 PathPlanner 页 →

数值优化 Choreo

照样拖航点，但思路不同。Choreo 不画样条，而是在机器人物理模型上跑数值优化器（CasADi），输出满足电机扭矩、轮胎抓地和加速度极限的时间最优 .traj。时间最优 —— 挤名次那 0.2 秒就靠它 —— 但迭代慢（求解器每次跑要几秒），模型给错了轨迹也错。

打开 Choreo 页 →

常见的坑

常见的坑

下面这些 auto 专属的坑，全出在模式切换和 auto 起步那一刻。大多在 code review 里看不出来，只有上了场才暴露 —— 每个踩过一次就不再上当。

  1. 01

    在 autonomousInit() 里忘了 schedule auto 命令

    如果 autonomousInit() 没对 getAutonomousCommand() 返回的命令调 schedule()，机器人会在整个 15 秒里一动不动。没有报错，也没有动作。永远确认 schedule() 这一行真的在。

  2. 02

    auto 跑进了 teleop（没取消）

    如果 teleopInit() 不取消 auto 命令，它会在 teleop 开始后继续跑，跟驾驶员抢底盘 —— 车像有了自己的想法。在 teleopInit() 里取消 auto 命令（或 cancelAll）。

  3. 03

    默认 chooser 选项把 pose 重置到了错的一侧

    每条 auto 都应以把机器人 pose 重置到已知起点开头，并处理好 alliance（红蓝镜像）。如果默认 chooser 选项把 pose 设成了错的一侧，整条路径会镜像着跑，机器人开向不知名的地方。把默认选项做得安全、且能区分 alliance。

  4. 04

    跳过赛前初始化 —— pose、gyro、预热

    在路径跑起来之前，把 pose 重置到已知起点、把 gyro 种到正确朝向，如果流程需要还要预先转动 intake 或给 flywheel 升速。漏掉这步，auto 的头一秒就耗在跟一个过期的 pose 或冷启动的机构较劲上。

  5. 05

    不清楚 auto → teleop 过渡时哪些状态会保留

    pose、gyro 朝向、传感器状态会从 auto 带进 teleop；被取消后的那条 auto 命令则不会。误以为 gyro 或 pose 会在 teleop 开始时“归零”，或以为 auto 已经干净地停住了某个机构，是 teleop 头几秒行为诡异的常见来源。
