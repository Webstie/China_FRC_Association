是什么 & 为什么

Choreo 是什么

Choreo 也是 GUI 应用，但思路不一样。你照样在场地上拖航点，但 Choreo 不画 spline —— 它跑一个数值优化器（CasADi），在机器人的物理模型上算轨迹。

输出是 .traj 文件：满足约束的时间最优轨迹，它在命中你的航点的同时，尊重电机扭矩、轮胎抓地和加速度约束。这条路径不只是顺滑 —— 而是机器人在物理上能跑出的最快路线。

如果你已经在 PathPlanner 里写过 auto，这套思路是相通的。航点是同一个概念，变的只是“航点之间那条曲线由谁决定”—— 是 solver，而不是你的手。

求解引擎 CasADi
输出文件 .traj
配套库 ChoreoLib
优化目标 时间最优

GUI 界面

Choreo 的 GUI 界面

你放下的是带约束的航点 —— 不是 spline。每个航点都可以指定：是否在此停下、要保持什么 heading、局部速度上限是多少。Choreo 还需要一个真实的机器人模型：质量、转动惯量、轮胎摩擦系数、传动比、电机扭矩曲线，以及保险杠 / 轴距 / 轮距等物理尺寸。

航点和模型都齐了，solver 跑一遍，生成 .traj 文件。这个求解步骤就是它和 PathPlanner 的根本区别：在你拿到曲线之前，一个真正的优化器先把物理啃过一遍。

生成的文件

Choreo 生成的文件

Choreo 的产物很小、很独立：每条轨迹一个 .traj 文件，放在项目里的 choreo/ 目录下。运行时 ChoreoLib 按名字加载它，所以文件名（去掉 .traj 后缀）就是你在代码里引用的句柄。

文件 代码加载方式
choreo/MyTraj.traj Choreo.loadTrajectory("MyTraj") （通过 ChoreoLib）

代码接入模式

代码接入模式

ChoreoLib 的入口是 AutoFactory。你在 RobotContainer 里启动期构造它一次，把它需要的几个钩子交给它：一个 pose supplier、一个 pose reset、一个把轨迹采样点转成轮速的函数、一个为红方 alliance 镜像路径的开关，以及作为 requirement 的 drive subsystem。

配置好之后，构造一个跟随 Choreo 轨迹的 auto 只需一行：autoFactory.trajectoryCmd("MyTraj") 返回一个可直接调度的 Command。你传入的名字对应 GUI 里那个 .traj 文件名。 

// Once at boot, in RobotContainer.
// 启动期配置一次。
AutoFactory autoFactory = new AutoFactory(
    drive::getPose,                // pose supplier
    drive::resetPose,
    drive::followTrajectory,       // sample → wheel speeds
    true,                          // mirror for red alliance
    drive                          // requires this subsystem
);

// Build an auto that follows a Choreo trajectory.
Command myAuto = autoFactory.trajectoryCmd("MyTraj");

从 GUI 到运行中的 Command，一共有六次交接。前四步发生在 Choreo 里；后两步是你的代码读取 GUI 存下的 .traj 文件。

  1. 01

    放航点

    在 Choreo GUI 里把航点拖到场地上 —— 起点、终点，以及路径必须经过的中间点。

  2. 02

    设约束

    为每个航点设置：是否停下、heading 约束、局部速度上限。这些约束是 solver 必须遵守的边界。

  3. 03

    求解

    Choreo 在你的机器人模型和约束上跑 CasADi 优化器。这一步要几秒，是整个流程里慢的那一环。

  4. 04

    存 .traj

    求出的轨迹被写进 choreo/ 目录下的 .traj 文件，等着你的代码按名字加载。

  5. 05

    AutoFactory(...)

    启动期一次，你的代码用 pose、reset、follow 钩子构造一个 AutoFactory。它在启动时读取这些 .traj 文件。

  6. 06

    autoFactory.trajectoryCmd("name")

    用轨迹名字调用 trajectoryCmd，构造出 Command。它和其他 Command-Based 命令一样可以调度。

强项与注意

强项与注意

当路径本身成为瓶颈时，Choreo 才显出价值。优化器尊重那些手画 spline 直接忽略的物理 —— 但正是这份对物理模型的依赖，也成了它的软肋。

强项 时间最优

差那 0.2 秒名次的，靠这个挤出来。Choreo 给你的是机器人物理上能跑出的最快轨迹，而不只是一条好看的曲线。

机器人能跑的最快
强项 尊重真实极限

求解器尊重真实电机扭矩和摩擦极限，少有“图上很美机器人跟不上”的情况。

电机扭矩 + 轮胎摩擦
注意 迭代慢

求解器每次跑要几秒到十几秒。PathPlanner 点一下就重存，而 Choreo 每改一处都要重新求解一次。

每次求解数秒
注意 模型错则轨迹错

模型给错了 → 轨迹也错。这里 garbage in garbage out 体现得淋漓尽致：质量、COF、传动比给错了，那条“最优”路径就是为一台你并不拥有的机器人算的。

模型必须准确

怎么选

PathPlanner vs Choreo 怎么选

两个工具都是在场地上放航点、再喂给 follower；区别在于“曲线由谁来画”以及“你能多快迭代”。PathPlanner 手画 spline、秒级重存；Choreo 跑数值优化，用迭代速度换来时间最优的结果。

维度 PathPlanner Choreo
方式 手画样条 数值优化
迭代速度 点一下就存（毫秒） 求解器（秒级以上）
最优性 顺滑但非最优 时间最优
事件标记 支持 支持（较新）
配套库 PathPlannerLib ChoreoLib
适合 多数队伍 / 第 1 周 冲淘汰赛名次

新手默认：先用 PathPlanner。Week 1 的 auto 20 分钟搞定，先把车送上场。瓶颈真的变成“路径本身慢了”再换 Choreo，别因为“我们写得不对”就归咎到路径上。

一个参考数据点：某成熟队伍的 25-26-swerve 项目用的就是 PathPlanner —— RobotContainer.java 里那一长串 NamedCommands.registerCommand 就是证据。能进决赛的成熟方案，这一题已经替你选过了。

常见的坑

常见的坑

Choreo 的麻烦大多来自“GUI 里的模型和代码里的配置对不上”，或是忘了 follower 本身还要调。这些都不会以编译错误的形式出现 —— 机器人只是默默偏出路径。

  1. 01

    GUI 里的机器人模型和真车对不上

    Garbage in, garbage out。如果你填的质量、轮胎 COF、传动比或电机曲线是错的，solver 会为一台你并不拥有的机器人算出“最优”轨迹，真车跟不上。相信路径之前，先把模型量准。

  2. 02

    AutoFactory 配置和 GUI 配置不一致

    你交给 AutoFactory 的 pose supplier、reset 和 follow 函数，必须描述 GUI 建模的那同一个 drivetrain。如果代码里的轮距或传动比和 .traj 不一致，follower 会和路径打架。把这些数字收在唯一的来源里。

  3. 03

    alliance 镜像翻转方向搞错

    AutoFactory 里那个“为红方镜像”的开关决定轨迹是否为红方 alliance 翻转。设错了，你的 auto 就跑成你画的那条的镜像 —— 机器人自信地朝着完全相反的方向开。两个 alliance 都要测。

  4. 04

    忘了 follower 本身还要调

    完美的 .traj 也只是一条参考。holonomic follower —— 那个把机器人拉回轨迹的 X、Y、rotation 三路 closed-loop PID —— 自己的增益也得调。follower 没调好，再优的路径也会跑得晃晃悠悠。
