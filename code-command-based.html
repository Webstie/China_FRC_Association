是什么 & 为什么

为什么有 Command-Based

如果你之前写过 Arduino 风格的代码，最直觉的做法是把一切都塞进一个大循环 — 读手柄、驱动电机、读传感器，一行一行串起来。这种模型在 FRC 机器人上很快就撑不住：底盘、intake、shooter、climber 需要同时运行、立即响应输入，还要共享硬件而不互相打架。

Command-Based 是 WPILib 给出的答案。机器人被拆成持有硬件的 Subsystem（每个机构一个）和描述动作的 Command（机器人能做的每件事一个），由一个 Scheduler 统一调度循环、随时决定哪条 Command 能使用哪个 Subsystem，让整体行为可预测。新手 90% 的时间都花在 RobotContainer 这一个文件里把这些片段连起来。

它真正的价值在于组合：小命令可以拼成 sequence、parallel、race、timeout，复杂的自动流程和遥控宏都是用你已经验证过的小块搭出来的，不用每个赛季都重新写状态机。

入口与接线文件 RobotContainer
每个机构一个 Subsystem
每个动作一个 Command
驱动整个循环 CommandScheduler

项目结构

项目里有什么

每个 Command-Based 项目都从同样的一组文件开始。按 Main → Robot → RobotContainer → Constants → 任一 subsystem 的顺序读一遍，整个框架就豁然开朗。

  • Main.java — 入口文件，把控制权交给 WPILib。不要改。
  • Robot.java — 各模式的生命周期钩子。最关键的一行是 robotPeriodic() 中的 CommandScheduler.getInstance().run()。
  • RobotContainer.java — 接线文件。subsystem 在这里创建、默认命令在这里设置、按键在这里绑定到命令、auto chooser 也在这里配置。新手 90% 的修改都落在这。
  • Constants.java — 所有可调数值集中在这里：电机 ID、PID 参数、场地尺寸、速度上限等。
  • subsystems/ — 每个机构一个文件，都继承 SubsystemBase 并持有硬件。
  • commands/ — 多步或较复杂的命令，不适合直接写成 subsystem 里的 factory method。

机器人启动过程

机器人是怎么跑起来的

从上电到第一次 teleop 循环，每次都会经过同样的五步。理清这条流程，出问题时就知道该打开哪个文件查。

  1. 01

    Main.main() → RobotBase.startRobot(Robot::new)

    JVM 从 Main.main() 开始执行，立即把控制权交给 WPILib。这个文件是自动生成的，不要改。

  2. 02

    Robot 构造函数 — 一次性完成接线

    WPILib 创建一个 Robot 对象。它的构造函数会创建 RobotContainer，进而创建所有 subsystem、设置默认命令、绑定所有 trigger。所有接线都发生在这一刻，早于任何模式开始。

  3. 03

    模式 init — 每次切换模式时跑一次

    机器人 enable 后，WPILib 会调用对应的 init 方法：auto 开始时调用 autonomousInit()，teleop 开始时调用 teleopInit()，disabled 时调用 disabledInit()，test 模式调用 testInit()。在这里调度 auto 命令或取消遗留任务。

  4. 04

    周期函数 — 每 20 毫秒，50 赫兹

    WPILib 每 20 毫秒调用一次 robotPeriodic() 和当前模式对应的 periodic（teleopPeriodic、autonomousPeriodic…）。robotPeriodic() 里最关键的一行是 CommandScheduler.getInstance().run()。

  5. 05

    CommandScheduler.run() 处理一切

    每次 tick，scheduler 都会轮询所有 trigger、调度新命令、调用每个 subsystem 的 periodic()、运行活跃命令的 execute()、检查 isFinished()，并清理已结束的命令。这一次调用驱动了整个 Command-Based 系统。

基本构件

四个核心部分

几乎所有 Command-Based 程序都由这四个部分组成。理解每个部分的职责后，整个框架就会变得清晰。

持有硬件 Subsystem

封装一个机构 — 底盘、intake、elevator、shooter。持有电机控制器和传感器，对外暴露高层方法，并每 20 毫秒自动运行一次 periodic()。

继承 SubsystemBase
描述一个动作 Command

一段短小的行为：前进两米、运行 intake 直到传感器触发、把游戏件投到指定位置。声明自己需要哪些 subsystem，方便 scheduler 处理冲突。

实现 Command 接口
绑定输入 Trigger

把任意布尔信号 — 按键、传感器、状态量 — 变成命令绑定：onTrue、whileTrue、onFalse、toggleOnTrue。CommandXboxController 直接为手柄按键提供 Trigger。

Trigger / CommandXboxController
运行循环 CommandScheduler

全局唯一的调度器：轮询 Trigger、调度 Command、调用每个 subsystem 的 periodic()、中断冲突命令、运行 default command。你只需要在 robotPeriodic() 中调用一次 run()。

CommandScheduler.getInstance()

从零开始

写一个 Subsystem

subsystem 封装一个机构。文件放在 subsystems/，继承 SubsystemBase，把硬件声明为 private 字段，构造函数里做配置。periodic() 由 scheduler 每 20 毫秒自动调用，常用来推 telemetry、读传感器，或跑那些“应该一直滴答的”状态机。

public 方法每个只做一件硬件动作（开电机、停、设目标位置）。Command factory method 返回可直接调度的 Command，且因为继承自 Subsystem，会自动 require this，几乎不用自己调 addRequirements。

底部的 intakeCommand() 用了 startEnd：命令开始时执行一次第一个 lambda，结束或被中断时执行一次第二个。命令活跃期间，scheduler 一直把这个 subsystem 占着；命令结束时，默认命令（如果有）会自动接管。 

package frc.robot.subsystems;

import com.revrobotics.spark.SparkMax;
import com.revrobotics.spark.SparkLowLevel.MotorType;
import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.SubsystemBase;

public class Intake extends SubsystemBase {

  private final SparkMax motor =
    new SparkMax(5, MotorType.kBrushless);

  public Intake() {
    motor.setInverted(false);
    // current limit, idle mode, etc.
  }

  @Override
  public void periodic() {
    // runs automatically every 20 ms
    // good place for telemetry / sensor reads
  }

  public void run(double speed) {
    motor.set(speed);
  }

  public void stop() {
    motor.set(0);
  }

  public Command intakeCommand() {
    return startEnd(
      () -> run(0.6),
      () -> stop()
    );
  }
}

Command 类

写一个 Command — 类的写法

当命令需要保存真正的内部状态（起始位置、PID、视觉数据等）时，写成 commands/ 下的完整类最清晰。构造函数接收需要的 subsystem，并调用 addRequirements(...) 让 scheduler 处理冲突。然后 override 四个生命周期方法。

  • initialize() — 调度时执行一次。在这里做初始化。
  • execute() — 活跃期间每 20 毫秒一次。循环体。
  • isFinished() — 每次 execute 之后被检查。返回 true 表示结束。
  • end(interrupted) — 停止时执行一次。务必把机构置于安全状态。
package frc.robot.commands;

import edu.wpi.first.wpilibj2.command.Command;
import frc.robot.subsystems.Drivetrain;

public class DriveDistance extends Command {

  private final Drivetrain drive;
  private final double targetMeters;
  private double startMeters;

  public DriveDistance(Drivetrain drive,
                       double targetMeters) {
    this.drive = drive;
    this.targetMeters = targetMeters;
    addRequirements(drive);
  }

  @Override
  public void initialize() {
    startMeters = drive.getDistanceMeters();
  }

  @Override
  public void execute() {
    drive.arcadeDrive(0.5, 0);
  }

  @Override
  public boolean isFinished() {
    double delta =
      drive.getDistanceMeters() - startMeters;
    return delta >= targetMeters;
  }

  @Override
  public void end(boolean interrupted) {
    drive.arcadeDrive(0, 0);
  }
}

Command factory method

写一个 Command — factory 写法

短小、无状态的动作没必要写整个类。WPILib 在 Subsystem 上提供了 factory method，用一两个 lambda 就能构造一个 Command。因为是在 subsystem 内部调用，会自动 require 本 subsystem，省去 addRequirements。

  • runOnce(Runnable) — 执行一次 lambda 就结束。
  • run(Runnable) — 每 20 毫秒执行一次 lambda，自己不会结束。
  • startEnd(start, end) — 开始时执行 start，被中断时执行 end。
  • runEnd(loop, end) — loop 每 20 毫秒执行一次，end 在中断时执行一次。
  • Commands.* — 不依赖某个 subsystem 的通用工具：waitSeconds、print、either、sequence、parallel…
// All defined inside a Subsystem class:

public Command openClawCommand() {
  return runOnce(() -> claw.set(0.4));
}

public Command intakeUntilSensorCommand() {
  return run(() -> motor.set(0.6))
    .until(this::hasGamePiece)
    .finallyDo(interrupted -> motor.set(0));
}

public Command climbCommand() {
  return runEnd(
    () -> climber.setPosition(TOP),
    () -> climber.hold()
  ).until(() -> isAtPosition(TOP));
}

// Standalone helpers — no subsystem needed:

Command pause = Commands.waitSeconds(0.5);
Command log   = Commands.print("at target");
Command pick  = Commands.either(
  goLeft, goRight, () -> isBlueAlliance);

默认命令

默认命令

subsystem 的默认命令在没有别的命令占用它时自动运行。最经典的用法是手柄驾驶：除非有自动瞄准、自动平衡或路径跟随接管，否则底盘应始终响应摇杆。在 RobotContainer 构造函数里通过 setDefaultCommand 配置。

默认命令必须以所附 subsystem 作为 required — 用该 subsystem 自己的 run() factory 构造时这一点会自动满足。当一条优先级更高的命令调度并占用同一 subsystem 时，默认命令会被自动打断；那条命令结束后，默认命令自动恢复。

如果不设默认命令，subsystem 在没有命令占用时就保持空闲。intake、shooter 一般就是这种 — 没有人主动要求就不动。 

public class RobotContainer {

  private final Drivetrain drive = new Drivetrain();
  private final CommandXboxController driver =
    new CommandXboxController(0);

  public RobotContainer() {

    // Default: arcade drive from sticks.
    // Runs whenever no other command uses `drive`.
    drive.setDefaultCommand(
      drive.run(() -> drive.arcadeDrive(
        -driver.getLeftY(),
        -driver.getRightX()
      ))
    );

    configureBindings();
  }

  private void configureBindings() {
    // ... button bindings go here
  }
}

触发器

把输入绑定到命令

Trigger 就是一个带命令绑定的布尔信号源。CommandXboxController 已经为每个按键和模拟输入提供了 Trigger。你也可以用任何布尔条件（传感器读数、当前 alliance、teleop 是否启用）构造自定义 Trigger，并用同样的方式绑定命令。所有这些都写在 RobotContainer 的 configureBindings() 里。

选对绑定方法很重要：onTrue 在信号上升沿调度一次然后就不管了，适合自己会结束的动作；whileTrue 在信号为 true 时持续运行，信号一变 false 立刻取消，适合“按住才执行”的动作；toggleOnTrue 第一次按下开始、第二次按下取消。 

private void configureBindings() {

  // --- Button bindings (CommandXboxController) ---
  driver.a().onTrue(intake.intakeCommand());
  driver.b().whileTrue(launcher.spinUpCommand());
  driver.x().toggleOnTrue(climber.climbCommand());

  // Analog and POV
  driver.rightTrigger().whileTrue(shooter.fireCommand());
  driver.povUp().onTrue(elevator.raiseCommand());

  // --- Composed button triggers ---
  driver.a().and(driver.b()).onTrue(specialMove);
  driver.x().or(driver.y()).onTrue(eitherShot);
  driver.leftBumper().negate().onTrue(safeMode);
  driver.start().debounce(0.5).onTrue(resetGyro);

  // --- Custom triggers from any boolean source ---

  // Auto-flash LEDs when intake grabs a game piece
  new Trigger(intake::hasGamePiece)
      .onTrue(candle.flashGreenCommand());

  // Only allow climb during the last 30 seconds
  new Trigger(() ->
      DriverStation.getMatchTime() < 30)
      .and(driver.back())
      .onTrue(climber.deployCommand());
}

完整示例

把所有部分拼起来

四个核心部分现在出现在同一处。subsystem 持有电机，用 startEnd 暴露一个 Command。RobotContainer 创建 subsystem、创建手柄，把 A 键绑定到该命令，使其在按住期间运行；松开按键，命令结束、stop() 自动被调用。

如果还需要一个空闲行为 — 比如没有发射任务时让 hood 轻轻保持在 0 — 也可以在这里写 shooter.setDefaultCommand(shooter.run(() -> shooter.holdZero()))。scheduler 会在没有更高优先级命令占用 subsystem 时跑默认命令。 

public class Intake extends SubsystemBase {

  private final SparkMax motor =
    new SparkMax(5, MotorType.kBrushless);

  public Command intakeCommand() {
    return startEnd(
      () -> motor.set(0.6),
      () -> motor.set(0.0)
    );
  }
}

public class RobotContainer {

  private final Intake intake = new Intake();
  private final CommandXboxController driver =
    new CommandXboxController(0);

  public RobotContainer() {
    // Hold A to run the intake; release to stop.
    driver.a().whileTrue(intake.intakeCommand());
  }
}

Command 生命周期

一个 Command 是怎么跑的

无论用类还是 factory 构造，每个 Command 都遵循同样的四步生命周期，由 scheduler 在和主循环相同的 20 毫秒节拍上推动。把这四步刻进脑子里，读和调试任何命令都会变成日常操作。

  1. 01

    initialize()

    命令被调度时执行一次。重置传感器、记录当前位姿、设定目标位置、启动计时器 — 任何只应在开始时做一次的事情。

  2. 02

    execute()

    命令活跃期间每 20 毫秒运行一次。这是循环体：按当前设定点驱动电机、跑一次 PID、刷新 telemetry。要写得轻，每秒会被调 50 次。

  3. 03

    isFinished()

    每次 execute() 之后被检查。返回 true 结束命令（到位、超时、传感器触发）；返回 false 继续运行。用 factory 构造的命令通常用 .until(...) 或 .withTimeout(...) 替代手写 isFinished。

  4. 04

    end(boolean interrupted)

    命令停止时执行一次 — 自然结束时 interrupted == false，被打断时 interrupted == true。务必在这里把机构置于安全状态：停电机、收气缸、清空目标。

组合命令

把命令组合起来

Command-Based 的真正威力是组合。小命令通过四个原语 — sequence、parallel、race、deadline — 拼到一起。绝大多数自动流程和遥控宏都是由现成的小块组合出来的，不必每次写新状态机。

顺序执行 sequence()

一条接一条执行，前一条结束后才开始下一条。适合分步流程：先开到位、再加速 shooter、再喂入并发射。

Commands.sequence(a, b, c) · a.andThen(b)
并行 — 都要结束 parallel()

同时启动所有命令，全部结束后整体才结束。适合多个独立动作并发执行，且都要完成的场景。

Commands.parallel(a, b) · a.alongWith(b)
竞速 — 谁先结束都算 race()

同时启动所有命令，任意一条结束时整体结束，其他被中断。经典用法：把不会自结束的动作和一个超时配对，让超时充当兜底。

Commands.race(intake.run(), Commands.waitSeconds(3))
截止 — 由一条决定时长 deadline()

同时启动；第一个参数是“截止命令”，它结束时其他命令一并取消。适合“某一条决定时长，其他都是配角”的场景：LED 闪烁、慢速驾驶、telemetry 辅助等。

Commands.deadline(intake.run(), drive.slow(), leds.flash())

除了这四个主要原语，Command 自身还有一组修饰方法，覆盖日常大多数场景而不必动 Commands.*。把它们链在任意 Command 上，可以加超时、加退出条件、加守卫，或在开始/结束时插钩子：

.withTimeout(seconds) .until(condition) .unless(condition) .onlyIf(condition) .repeatedly() .andThen(next) .alongWith(other) .beforeStarting(Runnable) .finallyDo(Runnable) .handleInterrupt(Runnable)

常见的坑

新手最容易踩的坑

第一年用 Command-Based 时浪费的时间，大半来自几个反复出现的小坑。这些坑在文档里都不显眼，但踩过一次以后就再也不会上当。

  1. 01

    robotPeriodic 里漏掉 CommandScheduler.getInstance().run()

    什么都不会跑：没有 periodic、没有命令、没有 trigger。机器人像断了线，每个按键都没反应。绑定不响应时永远先查这一行。

  2. 02

    Command 类里漏写 addRequirements()

    不写的话 scheduler 不知道这条命令需要某个 subsystem，冲突命令不会被中断。症状：两条命令争同一个电机，动作抖动或卡死。

  3. 03

    用 onTrue 绑定不会自己结束的命令

    onTrue 只在按下时调度一次，之后就不管了。如果命令自己永远不结束，会一直跑下去，直到被其他命令打断。需要松开按键就停的场景请用 whileTrue。

  4. 04

    设的默认命令没把该 subsystem 作为 requirement

    setDefaultCommand 要求默认命令的 requirements 包含该 subsystem。如果传入 Commands.run(...) 构造但没声明 requirement 的命令，启动时会抛 IllegalArgumentException。最简单的修法：用 subsystem.run(...) 代替 Commands.run(...)。

  5. 05

    在 RobotContainer 里直接调用 motor.set()

    subsystem 的意义就是让硬件只在一个地方出现。一旦 motor.set() 漏到接线文件，冲突检测就失去意义，调参也得跨文件找。把硬件访问留在 subsystem 里，让命令调用 subsystem 的方法。

  6. 06

    把同一个 Command 实例绑到两个不同的地方

    同一个 Command 同一时刻只能被调度一次。把 cmd 绑到两个按键并同时按下，第二次按下会被静默忽略，直到第一次结束。一律通过 factory method 生成新的实例，或用 Commands.defer 在调度时再构造。

  7. 07

    在 execute() 或 periodic() 里塞重活

    两个都以 50 赫兹运行。慢的循环会超出 20 毫秒节拍，Driver Station 会报 loop overrun，动作变得卡顿。把重活挪到 worker 线程、用计数器降频运行，或在节拍之间缓存结果。

  8. 08

    分不清 onTrue / whileTrue / onFalse / toggleOnTrue

    onTrue = 上升沿调度一次；whileTrue = 信号为 true 时持续运行，下降沿取消；onFalse = 下降沿调度一次；toggleOnTrue = 第一次按下启动，第二次按下取消。按动作语义挑对那一个。

下一步
